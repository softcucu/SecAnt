# 协议栈 / 解析器专项 checklist(各 lens 共用)

被审目标以网络协议栈/解析器为主时,除对应 lens 外,务必把下列**协议特有**问题点纳入清点与精读。

## 一、报文字段信任问题
- **长度字段**:`len/length/size/count` 解出后,是否在**读/写/分配/循环**前做了上下界夹紧?
  是否与"剩余缓冲区大小"比较过?`ntohs/ntohl` 后立刻夹紧了吗?
- **类型/标志字段**:`type/tag/opcode/flags` 是否被信任后直接索引跳转表/解释为某结构?越界 opcode?
- **偏移/指针字段**:报文里的 offset 用作 `buf+off` 是否校验 `off < buflen`?有无指针字段被直接解引用?

## 二、TLV / 分片 / 重组
- TLV 解析:`value_len` 是否可超出整个报文?嵌套 TLV 深度有无上限?
- 分片重组:多个分片的 `offset+len` 是否会**重叠/超界**写入重组缓冲?重组缓冲是否有总大小上限?
- 重组状态:乱序/重复/超时分片是否导致状态混淆、UAF、内存耗尽?

## 三、状态机
- **未认证态报文处理**:在握手/认证完成前,哪些报文类型被处理?能否借此触达本应受保护的解析路径?
- 状态跳变:能否用畸形/乱序报文把状态机推入非法态、死锁、或权限提升?
- 重放:已认证/已处理的报文能否重放产生效果?

## 四、收发与连接生命周期
- `recv/read` 返回值(短读、0=对端关闭、-1=错误、EINTR)是否正确处理?短读后是否误用未填满缓冲?
- 半关闭/断开/重连期间的悬垂状态与回调竞态(见 lens-race)。

## 五、空口 / 未认证单包 DoS(见 lens-dos)
- 设想攻击者只发**一个**精心构造的未认证报文:有没有任何字段能触发断言/空指针/除零/越界/无限循环?
  这类"single malformed packet → crash/hang"是协议栈最该优先排查的高危 DoS。

## 六、变体排查提示
确认某协议解析点有问题后,用 `rg` 把**所有同类解析函数**(同一 decode/parse 家族、同样从报文取 len/off 的模式)
列出来逐一核——协议栈里同种缺陷常在多个报文类型/服务里重复出现。
