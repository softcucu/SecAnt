# 审计方法论(proto-vuln-hunt 自带,通用)

本文件是 proto-vuln-hunt workflow 的**通用审计方法**。审计 agent 应在开始前通读本文,
协议相关目标还应读 `protocol-stack.md`。

> 前提:被审目标通常是**质量较好的代码仓**,简单工具一键可见的低级 bug 已很少。
> 真正有价值的发现来自**系统化清点 + 数据流精读 + 同类变体排查**,而非随机翻几个函数。

---

## 一、Phase A → Phase B(先清点,再逐站点精读)

不要"随便读几个函数就报"。按两阶段做:

**Phase A — 建候选站点清单(inventory)。**
围绕当前攻击树审计项、攻击方式或历史模式,用 **grep/rg 种子**在审计范围内枚举所有候选站点,记成一张小表:
`path:line | 表达式/调用片段 | 初判可疑点`。清点要真实覆盖,**不要用 `head`/`tail` 截断冒充覆盖**;
结果太多就按子目录/被调函数分片统计,并记录"已分片"。

**Phase B — 逐候选站点验证。**
对清单里的每个站点,用 `Read` 看真实代码,**回溯数据流**:从不可信输入源(source)一路跟到危险汇聚点(sink),
确认:① 输入是否真的攻击者可控;② 中途有没有校验/夹紧把它拦住;③ 是否真能到达(reachability)。
只有"可控 + 可达 + 无有效拦截"才算候选漏洞。

---

## 二、Coverage 纪律(每个模式都要交代,不许草草了事)

对当前审计对象衍生出的关键 bug 模式,审计结束时心里都要有结论,二选一:
- **filed** —— 报了 finding(给出具体站点)。
- **cleared** —— 跑了该模式的 Phase-A 种子且**确实为空**,或逐站点看过确认不可利用;一句话写明依据
  (例:"无 `system/popen/exec` 调用"、"所有 `memcpy` 长度均来自 `sizeof` 常量")。

**"没看到明显问题"不是有效结论**——那是没真正跑该模式。一个从未在你分析里出现过的模式 = 覆盖失败。

**即时复查种子(risk_notes)**:本轮没坐实成漏洞、但发现“当前路径安全依赖调用方校验,被调点本身不自洽”的
跨调用点隐患时,放进结果的 `risk_notes`,而不是硬凑成 finding。系统会立刻派专用 recheck agent 消费这些种子,
不会汇总成风险报告或存档。

**最典型、最该登记的一类**是「校验只在调用方、被调点本身不自洽」的**跨调用点**隐患:
你在审 A 函数时发现 A 调用 B,A 做了充分校验、这条路径没问题;但 B(或某个危险原语 / 共享 helper)的安全
**依赖调用方传入已校验的参数**,B 自身并不重新校验。这条路径安全 **≠** B 安全——
**全仓其它调用 B 的地方未必都做了等价校验**。此时把它作为即时复查种子,`note` 写清三件事:
① B 的位置(file:line);② B 保持安全所依赖的前提 / 不变量(例如"长度已被夹紧到 ≤ buf_sz""指针非空""已认证");
③ A 中做对该校验的正例位置与逻辑。recheck agent 会继续枚举其它调用方,包括“C 调 B 未校验但 C 的所有上游调用方均已完成等价校验”的情况。

其它可触发即时复查的隐患同理:长度校验分散(没有统一夹紧点)、错误路径未统一释放、魔数硬编码、缺乏深度 / 递归限制等。
普通审计结果只输出 findings 与 risk_notes;新的资产 / 攻击面 / 攻击方式由系统在审计项完成后单独做威胁分析增量识别,不要在本轮审计里扩大范围。

## 三、回合预算(防止无限深挖 / 卡死)

保持一个内部工具调用计数,遵守软硬上限:
- **软上限**:做了较多调用仍未开始产出时,停止扩大范围;就现有最强候选先精读、该报的报掉。
- **硬上限**:再往后必须收尾——把已分析确认的都报出来,跳过剩余;别为了凑满而硬撑。

典型一次干净审计应远低于上限。**reachability 追溯够用即可,不必追求完美调用链**——证据足够支持"可达且可控"就报。

---

## 四、Finding 写法(7 段式,与报告阶段一致)

确认一条漏洞时,信息按这 7 段组织(报告阶段会据此成文):
1. **漏洞描述** —— 为什么是漏洞:破坏了什么不变量、什么假设失效、攻击者控制什么。
2. **相关代码** —— 从源码摘真实片段(够上下文让 bug 一目了然),不要转述。
3. **数据流** —— 来源(不可信来源 path:line)/危险点(sink path:line)/校验(中途有无校验,有则为何不足)。
4. **可达性调用链** —— 从入口到 sink 的简短调用链。
5. **影响** —— 成功利用能达成什么(OOB 写 / 信息泄露 / 认证绕过 / RCE / DoS)。
6. **已检查缓解** —— canary / ASLR / FORTIFY / sanitizer / 类型上界等是否存在、可否绕过。
7. **修复建议** —— 怎么修。

一个站点一条 finding;同一根因出现在多个函数则拆成多条(各自的 path:line)。

---

## 五、坚守 bug 类别 + 同类变体排查

- **坚守 bug 类别**:一条 finding 归到某模式,前提是该模式的不变量独立成立;不要把同一根因硬塞进不相干的类别。
- **同类变体排查(variant analysis)**:确认/疑似某类问题后,用 `rg`/semgrep/tree-sitter/CodeQL(免编译)把**全仓同类站点**
  捞出来逐一核——有的放矢的定向排查,不是全仓盲扫。历史问题(history)模式尤其要这样横向扫一遍。

---

## 六、拒绝这些"偷懒否决理由"(验证阶段尤其重要)

判定误报必须**拿证据**,不得凭以下说法随手否决:
- "这条路径不可达" → 必须用 caller trace 证明;否则按可达处理。
- "有 ASLR/DEP/canary 挡着" → 缓解是绕过目标,不消除漏洞。
- "太难利用了" → 仍要报,利用难度交给严重度。
- "输入在别处校验过了" → 去**核实**那个校验确实存在且覆盖此路径。
- "只会崩溃,不可利用" → 内存破坏常常可控;崩溃本身在协议栈里也是 DoS。
- "环境是可信的" → 在 LOCAL_UNPRIVILEGED 下环境变量/路径/文件都算攻击者可控。
- "只有一个线程调用" → 线程使用方式会变;按可并发评估。

只有当你能**证伪可达性**、或**确证已有校验把输入夹紧**、或**确证根本不是 bug(误读代码)**时,才判误报。
